# 카드 삭제/등록 멈춤 — 백엔드 확인 요청

**To. 정재빈**
**From. 모바일**
**증상 요약:** 카드 목록에서 옛 카드가 삭제되지 않고 서버 응답이 오지 않음(hang). 이어서 카드 등록도 멈춘 것처럼 보임.

---

## 1. 결론 (뭘 봐줘야 하나)

DB에 **컬럼 값이 비정상인 옛 카드 행**이 있고, 그 행을 `DELETE` 할 때 **서버가 응답을 반환하지 않고 멈춥니다.** 새로 등록된 정상 카드는 정상 삭제됩니다.

- 새 카드 `DELETE /api/wallet/cards/26` → **200 OK, 삭제됨**
- 옛 카드 `DELETE /api/wallet/cards/24`, `/6`, `/2` → **응답 없음 (요청이 걸린 채 타임아웃)**

> 모바일은 요청을 정상적으로 보내고 있습니다(로그로 확인). 문제는 특정 legacy 행에서 서버가 응답을 못 주는 것입니다.

---

## 2. 근거

### (a) 삭제 로그
| cardId | 종류 | 응답 |
|---|---|---|
| 26 | 오늘 등록한 정상 카드 | `200 OK` (삭제 성공) |
| 24 / 6 / 2 | 예전에 등록된 옛 카드 | **응답 없음 (hang → 클라이언트 타임아웃)** |

### (b) 같은 행이 조회에서도 깨져 있었음
카드 목록 조회 시 아래 응답 때문에 클라이언트 파싱이 깨졌던 이력이 있습니다. 같은 행들이 원인으로 보입니다.

```json
{ "maskedCardNumber": "**** **** **** ****", "ownerName": null, "expiry": "94/61", "createdAt": ... }
```

- `ownerName` 이 `null`
- `expiry` 가 `"94/61"` 처럼 유효하지 않은 값

→ 즉, 이 행들은 **애초에 저장 시점에 값이 깨진 채로 들어간 데이터**로 보입니다.

---

## 3. 요청 사항 (둘 중 하나)

1. **데이터 정리** — DB에서 해당 legacy 카드 행(값이 null/비정상인 것들)을 직접 삭제하거나 값 보정.
   - 예: `ownerName IS NULL` 이거나 `expiry` 형식이 `MM/YY` 가 아닌 행 조회 → 정리
2. **삭제 로직 방어** — `DELETE` 처리 경로가 컬럼 값이 비정상인 행에서도 멈추지 않고 정상적으로 삭제 후 응답을 반환하도록 수정.
   - 지금은 어딘가(직렬화/검증 등)에서 예외 없이 **행이 걸린 채 응답이 안 나가는** 상태로 추정됩니다.

추가로, **어떤 경우에도 타임아웃 대신 에러 응답(4xx/5xx)이라도 내려주면** 클라이언트가 사용자에게 안내할 수 있습니다. 지금처럼 응답 자체가 없으면 클라이언트는 무한 대기만 하게 됩니다.

---

## 4. 참고 (모바일에서 한 조치)

문제를 고친 게 아니라 **드러나게 + 덜 꼬이게** 처리했습니다. 백엔드 수정과 별개입니다.
- 삭제 실패를 삼키지 않고 사용자에게 표시
- 무응답 카드 연타 방지(요청이 쌓이지 않게)
- 등록 중복 제출 방지
