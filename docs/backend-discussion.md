# 백엔드 협의 필요 사항

지금까지 앱에 구현한 기능과, **더 진행하려면 백엔드와 합의·구현이 필요한 것들**을 정리한다.
클라이언트는 모든 항목을 "서버가 아직 없어도 앱은 정상 동작"하도록 방어적으로 짰다.
아래 표의 서버 작업이 채워지면 실제 두 기기 연동이 완성된다.

우선순위: **P0** 없으면 핵심 기능 불가 · **P1** 경험 크게 개선 · **P2** 있으면 좋음

---

## A. FCM (백엔드 결정: 사용) — 상세는 `fcm-integration.md`

| # | 항목 | 우선 | 서버가 할 일 |
|---|---|---|---|
| A-1 | 토큰 등록 | P0 | `POST/DELETE /devices/push-token`. `token→userId` 매핑 저장(계정당 다중 기기 = 토큰 리스트) |
| A-2 | 보호자 알림 발송 | P0 | 자녀 사건 감지 시 부모 토큰으로 **data 전용** 푸시(`kind=PARENT_ALERT`) |
| A-3 | 자녀 명령 발송 | P0 | 부모의 캡처/촬영 요청 시 자녀 토큰으로 **data 전용** 푸시(`kind=CHILD_COMMAND`) |
| A-4 | 메시지 형식 합의 | P0 | `fcm-integration.md` 3절의 data 키(`kind/type/title/body/childId/id/requestId`) 확정 |
| A-5 | 우선순위·TTL | P1 | 안전 알림은 `priority=high`. 만료 시간 정책 합의 |

**주의:** `notification` 필드를 넣으면 백그라운드에서 시스템이 트레이에 임의로 띄워
자녀 명령을 가로챈다 → 반드시 **data 전용**.

## B. 알림 파이프라인 (자녀 사건 → 부모)

앱은 4종 안전 사건을 자녀 기기에서 감지해 로컬에 남기고, 아래 경로로 부모에게 전달한다.
**최종적으로는 서버가 알림을 만들어 줘야** 부모가 받는다.

| # | 사건 | 우선 | 서버가 할 일 |
|---|---|---|---|
| B-1 | 유해 사이트 차단 | P0 | 자녀 `POST /harmful-access/report` 수신 → 부모 알림 생성 + FCM. **이게 없으면 유해 차단은 부모에게 전할 방법이 아예 없다**(읽기 API 도 없음) |
| B-2 | 안전구역 이탈/도착 | P1 | 자녀 위치 + geofence 로 서버가 판정해 알림 생성. (없으면 앱이 위치·구역 API 로 직접 판정 — 이미 구현) |
| B-3 | 앱 사용량 한도 | P1 | `POST /children/{id}/app-usage` 합계가 한도 초과 시 알림. **한도 값을 주는 필드가 명세에 없음**(GAP-12) → 아래 D-1 |
| B-4 | GPS 꺼짐 | P1 | `POST /devices/gps-status` 수신 → 부모 알림. (없으면 앱이 위치 신선도로 추정 — 이미 구현, 단 "추정"이라 문구가 약함) |
| B-5 | 자녀 사건 동기화 경로 | P1 | `POST/GET /children/{childId}/alerts` (`child-push-contract.md` 4절). 자녀 홈 「최근 알림」 원본을 부모가 그대로 받는 가장 정확한 경로 |
| B-6 | 알림에 자녀 식별자 | P1 | `GET /notifications` 응답의 `NotificationDto` 에 `childId` 추가. **없으면 다자녀 부모의 대시보드 자녀별 필터가 무력화**(모든 자녀에게 공통 표시로 처리) |
| B-7 | 알림 읽음 동기화 | P2 | 앱은 현재 읽음을 로컬에만 반영. `PATCH /notifications/{id}` 를 실제로 연동할지 결정 |

## C. 캡처 / 카메라 요청 (부모 → 자녀)

부모 마이페이지의 「화면 캡처」·「카메라 촬영」 요청이 쓰는 경로. 둘은 대칭이다.

| # | 항목 | 우선 | 서버가 할 일 |
|---|---|---|---|
| C-1 | 캡처 요청 | P0 | `POST /children/{id}/screenshots/request` → 자녀에 `SCREEN_CAPTURE` 명령(FCM 또는 소켓) |
| C-2 | 카메라 요청 | P0 | `POST /children/{id}/photos/request` → 자녀에 `CAMERA_SHOT` 명령 (`child-push-contract.md` 5절) |
| C-3 | 촬영본 조회 | P0 | `GET /children/{id}/photos` (페이지) — 부모 「카메라 촬영」 갤러리 |
| C-4 | 업로드 | P0 | `POST /children/{id}/screenshots`, `POST /children/{id}/photos` (multipart). 이미 클라이언트 구현됨 |
| C-5 | 완료 통지 | P1 | 업로드 완료 후 부모에게 FCM(선택). 없으면 부모 앱이 폴링(캡처 2분/카메라 5분)으로 확인 |
| C-6 | ~~명령 pending 백업~~ | — | **철회(2026-08-28)** — `GET .../commands/pending` 폴링은 클라이언트에서 제거. 요청 없음 |
| C-7 | 명령 처리 결과 회신 | P1 | `POST /children/{id}/commands/{requestId}/ack` (`child-push-contract.md` 2절). 소켓 ACK 과 **멱등** 처리 필요. FCM 이 소켓 꺼진 상태로 도착하면 이 경로가 유일한 회신 수단 |

## D. 명세 자체의 구멍 (GAP) — 정책 결정 필요

| # | GAP | 우선 | 결정할 것 |
|---|---|---|---|
| D-1 | 앱 사용 한도 필드 없음 (GAP-12) | P1 | `children/{id}` 에 일일 한도(분) 필드 추가 여부. 지금은 클라이언트 상수 180분 |
| D-2 | 차단 목록 itemId 없음 (GAP-04) | P1 | `GET /blocklist` 가 문자열 배열이라 삭제 대상 id 가 없음. `{ id, listType, keyword }[]` 로 스키마 변경 요청. 지금은 키워드 문자열을 id 로 대용 |
| D-3 | 차단 카테고리 개념 없음 (GAP-04) | P2 | 성인/도박/폭력/마약 4카테고리를 서버가 관리할지, 클라이언트 키워드 묶음으로 둘지. 지금은 클라이언트 사전 |
| D-4 | 차단 앱 수 API 없음 (GAP-03) | P2 | 대시보드 「차단된 앱 N개」가 상수. 실값 API 필요 여부 |
| D-5 | 벌크 차단 등록 | P2 | 카테고리 ON 시 키워드가 최대 18건 개별 POST. `POST /blocklist/bulk` 있으면 1회로 축소 |
| D-6 | 용돈 지갑 (GAP-05) | P2 | `child-push-contract.md` 3절 제안 계약 확정 |

## E. 인증 / 역할

| # | 항목 | 우선 | 서버가 할 일 |
|---|---|---|---|
| E-1 | role 표기 | P0 | 로그인 응답과 `GET /users/me` 의 role 문자열 확정. 앱은 `PARENT/CHILD/ROLE_CHILD/child/KID/GUARDIAN` 등을 관대하게 파싱하지만, **서버가 실제로 PARENT 를 주면 자녀도 부모로 로그인**됨 → 계정 데이터·응답 확인 필요 |
| E-2 | 다중 기기 세션 | P1 | 한 계정을 두 기기에서 로그인(테스트 시나리오)했을 때 토큰/세션 정책 |

## 지금 앱이 "서버 없이" 버티는 방식 (참고)

백엔드 작업 전에도 데모가 되도록, 클라이언트가 아래로 대체하고 있다.
서버 구현이 들어오면 자동으로 실경로가 우선한다(중복 없음, id 기반 dedup).

- **유해/GPS/사용량/이탈** → 앱이 읽기 API 로 직접 판정(`ParentChildWatcher`) + 자녀 사건 업로드(`ChildAlertUploadWorker`)
- **알림 목록** → 로컬 보관함이 원본, 서버 응답과 합침(`ParentAlertStore`, 계정별 파일로 영구 저장)
- **캡처/카메라 요청** → 목업은 같은 프로세스 명령 버스로 흐름 시뮬레이션
- **FCM** → 토큰 레지스트라·라우터는 완비, Firebase 글루만 대기(`fcm-integration.md`)

---

## 요약: 두 기기 실연동에 꼭 필요한 최소치 (P0)

1. FCM: 토큰 등록(A-1) + 보호자 알림 발송(A-2) + 자녀 명령 발송(A-3) + 형식 합의(A-4)
2. 유해 차단 알림 생성(B-1) — 유일하게 클라이언트가 대체 불가한 사건
3. 캡처/카메라 요청·조회·업로드(C-1~C-4)
4. role 표기 확정(E-1)

이 넷이면 요청하신 시나리오(자녀 4종 감지 → 부모 푸시+대시보드, 부모 요청 → 자녀 촬영 → 부모 목록)가
두 기기에서 완전히 돈다.
